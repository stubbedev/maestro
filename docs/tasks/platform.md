# Task: internal/platform — Composer\Platform and the PHP runtime probe

Composer runs inside PHP, so Composer\Platform\Runtime answers questions about the running PHP in-process (constants, extensions and their versions, phpinfo sections, classes, function calls). maestro runs `php` as a child process instead.

1. Port .ref/composer/src/Composer/Platform (Runtime, Version, HhvmDetector) faithfully.
2. Implement Runtime in Go backed by a probe: an embedded PHP script (go:embed) run once with the user's `php` (found as Composer would find the PHP it runs on — PHP_BINARY semantics: maestro uses `php` on PATH unless COMPOSER_PHP / config says otherwise; check what Composer itself honours and document the rule) that collects, in one invocation, everything any Runtime call in Composer's code can ask: grep .ref/composer/src for `Runtime` users (Repository/PlatformRepository.php is the big one: getConstant ×20, getExtensionInfo ×20 (phpinfo per extension — capture each loaded extension's info output), getExtensions, getExtensionVersion, hasClass, hasConstant, invoke ×3) plus the other in-process PHP facts maestro needs elsewhere: PHP_VERSION, PHP_OS, PHP_BINARY, php_uname values used in the User-Agent, ini values (short_open_tag for internal/classmap, memory_limit, allow_url_fopen, openssl.cafile/capath for internal/util/http's CA search, …), loaded ini files (php_ini_loaded_file + php_ini_scanned_files for util.IniGetAll), xdebug state, extension list with versions, OPENSSL/ICU/curl/libxml/... library versions exactly as PlatformRepository derives them. Return it as a typed snapshot; answer Runtime calls from it. Runtime methods that can't be answered from a snapshot (arbitrary invoke) must be enumerated: list every call site's arguments and make sure the probe covers them.
3. Cache the probe result on disk under maestro's cache dir, keyed by everything that can change the answer (php binary path + size + mtime, PHP_INI_SCAN_DIR, PHPRC, the loaded ini files' paths + mtimes as listed by a cheap check, -d options passed via COMPOSER env?) — measure the probe cost first; if it's under ~30 ms consider whether caching is worth the staleness risk, and document the decision. Concurrency-safe.
4. A clean error path when php is missing: Composer itself can't run without PHP, but maestro can still do many things (e.g. install with --ignore-platform-reqs, or config.platform.php set). Decide what needs php and produce Composer-like errors only where a value is actually needed; document.

Tests: port .ref/composer/tests/Composer/Test/Platform/* and the Runtime-related parts of Test/Repository/PlatformRepositoryTest (the PlatformRepository port itself comes later with internal/repository — but make sure the Runtime API you expose lets that test be ported 1:1: it mocks Runtime with exact call/return expectations, so expose Runtime as an interface with the PHP method set). Oracle: run the probe and compare against what Composer's real Runtime returns in PHP for the same php (tools/oracle/platform), for several php builds available via nix (php82, php83, php84 with different extension sets).

Scope: internal/platform, tools/oracle/platform. Use internal/util (ProcessExecutor, ExecutableFinder, IniHelper) and internal/php.
Report: public API, probe cost and caching decision, test counts, lint/test status.
