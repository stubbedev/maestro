# Task: design the PHP plugin shim (docs/PLUGINS.md) — no Go code

Composer plugins and PHP-callable scripts (`Vendor\\Class::method`, which receive Composer\Script\Event and call $event->getComposer()) call Composer's PHP API in-process. maestro is Go, so it needs a PHP shim: PHP classes under the real Composer\ names, embedded in maestro and run by the project's `php`, that plugins load against, backed by maestro's Go state over IPC, so plugins work unchanged.

1. Survey real plugins (fetch latest releases into a scratch dir under .ref/plugins/ with composer): composer/installers, pestphp/pest-plugin, phpstan/extension-installer, symfony/flex, symfony/runtime, php-http/discovery, dealerdirect/phpcodesniffer-composer-installer, cweagans/composer-patches (1.x and 2.x), wikimedia/composer-merge-plugin, bamarni/composer-bin-plugin, ergebnis/composer-normalize, composer/package-versions-deprecated, Illuminate\Foundation\ComposerScripts (laravel/framework), drupal/core-composer-scaffold, oomphinc/composer-installers-extender, mnsami/composer-custom-directory-installer, phpro/grumphp, captainhook/hook-installer, infection/extension-installer, tbachert/spi, and the stubbedev/*-mcp packages in /home/stubbe/git/work/kontainer/composer.json (read only; don't modify that repo). Per plugin: Composer classes/interfaces/methods/constants/events used, what it does at which event, what it mutates (install paths via custom installers, root requires before solving, repositories, PRE_POOL_CREATE filtering, files, autoload, CommandProvider commands, IO, prompts). docs/plugins-survey/ may already hold partial survey data from an earlier run; reuse and complete it.
2. Derive the required API surface, ranked by use: Composer/PartialComposer getters, Config::get, IOInterface, EventDispatcher (addSubscriber, dispatch, priorities), event classes and constants (ScriptEvents, PackageEvents, PluginEvents, InstallerEvents), Package interfaces/classes and methods, RepositoryManager / installed repository queries, InstallationManager (addInstaller, getInstallPath), InstallerInterface and LibraryInstaller subclassing (composer/installers extends it), Capability\CommandProvider with Composer\Command\BaseCommand (Symfony Console commands in PHP), Util\Filesystem, ProcessExecutor, Semver, JsonFile, Factory::getComposerFile, Installer (merge-plugin and bin-plugin run nested installs). Mark what is Composer-internal and may be refused.
3. Architecture: process model (long-lived php child per run, started lazily only if a plugin or PHP-callable script exists; plugin class loading as .ref/composer/src/Composer/Plugin/PluginManager.php does), IPC protocol (e.g. JSON-RPC over inherited pipes, calls both ways, event dispatch both ways), mirroring Go data into PHP (lazy proxies vs snapshot+diff), how plugin mutations flow back before the next step (root package before resolution, installers per package type, install path queries during install, pool filtering), how Symfony Console classes for CommandProvider plugins are provided (symfony is MIT and not Composer's code — weigh vendoring symfony/console PHP sources vs minimal reimplementations), output interleaving with identical output to Composer, exceptions and exit codes identical, --no-plugins, allow-plugins (Go side), plugin API version checks, startup cost/opcache, security (only allowed plugins load).
4. Test plan: per surveyed plugin an e2e fixture where real Composer 2.10.3 and maestro must produce identical vendor trees, lock files and output.

Write docs/PLUGINS.md: survey summary table, required API checklist, architecture, IPC message spec, the Go-side interfaces needed from other packages (repository, installer, eventdispatcher, config, io), phased implementation plan, test plan, risks. Concrete and precise — it is the spec for the implementers.
